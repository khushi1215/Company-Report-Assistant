# KNOWLEDGE.md — Company Report Assistant

A living decision log, updated as the project happens, not after.

---

## 1. Project Definition

Company Report Assistant is a chatbot that answers questions about Indian companies using their real annual reports as the source of truth. A user picks a company, types a question in plain English, and gets an answer pulled directly from that company's actual report text, along with a way to check exactly where the answer came from. This uses an approach called **RAG**, short for Retrieval Augmented Generation, meaning the chatbot searches the real document first and answers only from what it finds there, instead of answering from general knowledge.

---

## 2. Tech Stack + Why

### Why LangChain over LlamaIndex
**Considered:** LlamaIndex, another retrieval orchestration framework with strong document-indexing support.
**Chosen:** LangChain.
**Reasoning:** Both frameworks solve the same core problem. LangChain has broader adoption and stronger community documentation for building a full pipeline end to end, from chunking through to the final answer chain. Picked one framework to go deep in, rather than splitting effort learning two shallowly.

### Why Chroma over Pinecone or Weaviate
**Considered:** Pinecone and Weaviate, both hosted vector databases with more scaling features.
**Chosen:** Chroma.
**Reasoning:** This project works with 5 documents, not thousands. Chroma runs locally, is free, and needs no cloud account to get started. A hosted vector database would add infrastructure this project does not need at its current size. This reasoning still holds for local development, which continues to use Chroma unchanged. See the v2.0 entry below for why Pinecone was added later, specifically to solve a deployment memory constraint, not because this original choice was wrong.

### Why BAAI/bge-base-en-v1.5, over all-MiniLM-L6-v2 or OpenAI embeddings
**Considered:** OpenAI's embedding API as an alternative to a free local model. Also started with `sentence-transformers/all-MiniLM-L6-v2`, a smaller, faster free Hugging Face model, as the first real choice.
**Chosen:** `BAAI/bge-base-en-v1.5`, a larger free Hugging Face model, specifically trained for retrieval tasks (matching short questions to longer passages), rather than general sentence similarity.
**Reasoning:** `all-MiniLM-L6-v2` was used first and worked, but running the manual evaluation set surfaced a real, specific failure: it could not reliably tell apart chunks like "US business contributed 29% of revenue" from "India contributed 34% of revenue" elsewhere in the same report, both were structurally very similar sentences, and the smaller model's limited resolving power confused them. Diagnosed this directly by comparing raw retrieval rankings before and after switching models (see Discoveries above), confirming the swap genuinely fixed the specific case tested, a previously invisible correct chunk moved from absent-in-top-15 to rank 4. OpenAI's embedding API was not used, staying consistent with the earlier decision to avoid ongoing API cost for a project this size. Switching models required a full, one-time rebuild of the vector store, a real, several-hour cost on CPU-only hardware, accepted because it fixed a genuine, diagnosed accuracy problem rather than a guessed one.

### Why this project was not deployed live (v1.0 decision)
**Considered:** Docker on Render, at increasing tiers as real memory requirements were measured (free and $7/month tiers, both capped at 512MB, then $25/month Standard at 2GB, then $85/month Pro at 4GB). Also considered Streamlit Community Cloud, which turned out to have the same ~1GB ceiling and, more fundamentally, isn't built to run a separate background service like Ollama at all. Also considered switching the deployed LLM to a free hosted API (Groq) to remove the local model's memory requirement entirely.
**Chosen:** No live deployment for v1.0. The app ran fully, correctly, and was demoed locally.
**Reasoning:** Real memory usage was measured directly, not estimated, using Windows process monitoring, roughly 941MB for the app itself (embeddings model, Chroma, Streamlit, LangChain) plus roughly 2GB more if running the LLM locally via Ollama. That ruled out every free tier checked at the time. Switching the deployed LLM to Groq's free API would have solved the LLM's memory cost, but the app's own footprint alone still exceeded free-tier limits everywhere, meaning even with that swap, a paid tier (at least $25/month) would still have been required. Weighed against the ongoing monthly cost, and after already investing significant, real effort in diagnosing and fixing retrieval accuracy (see Discoveries and Changelog), the decision at the time was to stop and document this clearly rather than add more moving pieces under time pressure. This was a deliberate, evidence-based decision, not an unfinished task, real infrastructure constraints were measured, real costs were weighed, and a clear line was drawn. This entry is kept as-is below, since it was the correct, honest call given what was known at the time. See the v2.0 entry directly below for what changed.

### v2.0: making free deployment possible by moving storage and embedding off the container
**Considered:** Staying with v1.0's fully local architecture and simply accepting no live deployment, permanently. Also considered paying for a bigger Render tier as a simpler, if costlier, fix.
**Chosen:** Keep the exact same RAG pipeline, LLM, LangChain, and Hugging Face foundation from v1.0, but move two specific pieces off the deployed container: the vector store (chunks) to a hosted vector database (Pinecone, free tier), and the query-time embedding step to a hosted Hugging Face inference API, alongside the already-scoped Groq swap for the LLM. Local development keeps using Chroma and a locally-loaded embedding model exactly as before, unchanged.
**Reasoning:** The v1.0 memory measurement showed the deployed container needed roughly 941MB just for the app itself, most of it from loading the embedding model and its underlying PyTorch dependency into memory, plus the vector index. Neither of those actually need to live inside the app's own container, a vector database can be queried over the network from a separate hosted service, and a single short question can be embedded by calling an API instead of loading a full model locally. Pinecone's free tier (2GB storage, roughly 350,000 vectors) comfortably fits this project's real size (6,282 chunks total after the 1300/200 chunk size revision), confirmed by checking actual current free tier limits rather than assuming. Combined with the already-planned Groq swap for the LLM, this removes the three heaviest pieces from the deployed app entirely, leaving only Streamlit and lightweight networking code, small enough to plausibly fit a free hosting tier, something v1.0's architecture could never do regardless of which platform was tried. Nothing about the actual engineering work changes: the same embedding model, the same hybrid retrieval logic, the same evaluation results, the same LangChain orchestration all carry over unchanged, this is purely a change in where things run, not what was built or why.

### Why chunk size changed from 1000/150 to 1300/200
**Considered, initially:** Smaller chunks (around 300 to 500 characters) for tighter, more precise matches. Larger chunks (around 2000+ characters) to preserve more surrounding context per match.
**Chosen, initially:** 1000 characters, 150 character overlap, using LangChain's `RecursiveCharacterTextSplitter`. Reasoning at the time: sampled pages showed dense paragraph writing, particularly in the FMCG and Energy sector reports, both averaging over 3800 characters of extractable text per sampled page, and 1000 characters generally held one full idea without diluting it across too much unrelated text.
**Revised to:** 1300 characters, 200 character overlap, after the evaluation set surfaced a real coherence problem, an answer that read like scrambled source text repeated rather than properly synthesized, alongside the ongoing infographic-page retrieval issue (see Discoveries and Challenges). Larger chunks keep more of a sentence or idea together, reducing the chance of a fact getting split away from its own context at a chunk boundary.
**Reasoning:** The original 1000/150 setting was a reasonable starting point, not a mistake, but it was never tested against real question and answer accuracy until the evaluation set was built and run. Once real evidence showed a coherence problem worth fixing, chunk size became one of three changes made together in the same round (alongside a prompt fix and a BM25 normalization fix). Retesting confirmed real improvement on the specific cases that were failing. The chunk size change required a full vector store rebuild, dropping the total chunk count from 7,995 (at 1000/150) to 6,282 (at 1300/200) across all 5 companies, fewer, larger chunks, as expected.

### Why Ollama with Llama 3.2, over Anthropic or OpenAI's API
**Considered:** Anthropic's Claude API and OpenAI's GPT API, both strong options for the final answer generation step, with Claude in particular known for following strict "only use the provided context" instructions well. Also considered Llama 3.1 8B as the local model before switching to the smaller Llama 3.2 3B.
**Chosen:** Ollama, running Llama 3.2 3B locally.
**Reasoning:** Both Claude and OpenAI require adding paid credit to an API account, no free tier for ongoing use. For a portfolio project of this size, spending money was not necessary when a genuinely capable free option exists. Ollama runs locally at no cost, with no API key and no usage limit. Llama 3.1 8B was tried first and worked correctly, but response time on this machine's CPU (no dedicated GPU, integrated Intel Iris Xe graphics only) was slow enough to hurt the actual experience of using the app. Switching to Llama 3.2 3B, a smaller model, cut response time noticeably with an acceptable drop in answer depth. The real trade-off, documented honestly, is that local models are slower to respond than a paid API and answer quality is a step below Claude or GPT-4 class models, and the smaller 3B model trades a bit more quality for speed compared to the 8B version. That trade-off is acceptable here, since the goal of this project is a working, well-documented RAG pipeline, not the fastest or highest-end possible answer quality.

### Why page citation is shown separately from the main answer, not inline
**Considered:** Putting the page number directly inside the answer text itself, for example ending every answer with "(page 47)".
**Chosen:** A short source line below the answer, plus a separate tab with the full retrieved chunk and page number.
**Reasoning:** Most people reading an answer do not need a page number inside the sentence itself. But removing it completely would remove the main trust signal of a RAG system, that an answer is grounded in a real, checkable document. The middle ground keeps the main answer clean while keeping verification easy to reach.

## 3. Data / System Overview

**Input data:** Five Indian companies' latest annual reports, one company per sector, chosen as sector leaders:

| Company | Sector | Pages | File size | PDF format |
|---|---|---|---|---|
| HDFC Bank | Banking and Finance | 629 | 17.7 MB | Text-based, no OCR needed |
| TCS | IT and Technology | 360 | 21.1 MB | Text-based, no OCR needed |
| HUL | FMCG | 244 | 29.2 MB | Text-based, no OCR needed |
| Reliance Industries | Energy and Oil and Gas | 147 | 9.2 MB | Text-based, no OCR needed |
| Sun Pharma | Pharma and Healthcare | 344 | 8.2 MB | Text-based, no OCR needed |

Checked using `pdfplumber` by sampling the first two pages and one middle page of each report and confirming extractable text was present. All five passed, none require OCR.

**Data flow:**
1. Each PDF is loaded and text is extracted with `pdfplumber`.
2. Text is split into chunks using LangChain's `RecursiveCharacterTextSplitter`, 1300 characters with 200 character overlap (revised from an initial 1000/150 after real evaluation evidence, see Tech Stack section).
3. Each chunk is converted into an embedding and stored in Chroma, tagged with company name and page number.
4. User selects a company, which filters retrieval to only that company's stored chunks.
5. User's question is embedded and compared against stored chunks to find the closest matches.
6. Matched chunks and the question are sent to the LLM, which generates an answer grounded only in those chunks.
7. Answer is shown with a short source line, full chunk detail available in a separate tab.

**Early assumption worth flagging:** the pipeline assumes each report's text extracts cleanly enough that a single chunk lands on a reasonably coherent block of text. Reports with heavy tables or multi-column layouts may extract messier than plain paragraph text does. This turned out to be a real, confirmed issue, not just a theoretical risk, see Discoveries and Challenges below for the infographic-page retrieval problem this caused.

## 4. Discoveries & Findings

- All 5 reports came back as real, extractable text on the sampled pages, none needed OCR. This was not guaranteed going in, PDF quality was expected to vary more given that Indian companies do not follow one standard reporting format.
- HDFC Bank's report is close to double the page count of the next largest report (629 pages versus 360 for TCS). This size difference was not anticipated when the 5 companies were picked based on sector leadership alone, and will need to be handled cleanly by the chunking step rather than assumed away.
- Character density per page varies a lot by sector. HUL and Reliance Industries averaged over 3800 characters per sampled page, while HDFC Bank and TCS averaged closer to 1200 to 1500. This suggests report writing style differs meaningfully by sector, which is part of why sector diversity was chosen for this project in the first place.
- Full extraction across all 5 PDFs confirmed the sampled-page check was reliable. Only **1 page out of 1,723 total pages** across all reports had no extractable text, from HDFC Bank's report, likely a cover page or an image-only page. Extraction otherwise worked cleanly on every page, no OCR needed anywhere.
- Switching from Llama 3.1 8B to Llama 3.2 3B, combined with reducing retrieved chunks from 4 to 3, brought real answer generation time down to roughly **14 to 18 seconds** per question on this machine (CPU only, no dedicated GPU). This is a genuine, felt improvement over the 8B model, confirmed through actual repeated use, not just a theoretical expectation from picking a smaller model.
- Running the full 18-question evaluation set surfaced a real, consistent pattern in where the system struggles. Roughly a third of questions returned wrong or missing content, and nearly all of those failures cluster around one specific type of source page: dense, infographic-style stat pages, rather than regular prose. For example, TCS's own financial highlights page extracts as `"Revenue Growth Industry-leading EPS Growth ... 4.6% Operating Margin 25.0% 8.8%"`, a real sentence-shaped jumble caused by a 3-column visual layout being flattened into one text stream during extraction. Numbers and their labels get visually scrambled in a way that plain prose never does. Pages with real narrative writing (for example, Reliance's Jio financial performance section) retrieved correctly and answered accurately. Pages built as stat grids or dashboards (HDFC's key metrics page, TCS's integrated business model page, Sun Pharma's US business overview page) were the source of most retrieval misses, even though the actual answer text was confirmed, by hand, to be present on those pages.
- A second, smaller pattern: on the largest reports (HDFC Bank, TCS, Reliance), broad questions like "how does the bank manage risk" sometimes retrieved a real but different section than the one originally picked for the evaluation set, since these large reports repeat similar themes (risk, digital strategy, partnerships) across many separate sections. The retrieved content was often still real and accurate, just not the specific passage expected, which matters less for the app's usefulness than a true wrong answer would, but is worth being aware of.
- Re-tested the Sun Pharma US business question after switching embedding models from `all-MiniLM-L6-v2` to `BAAI/bge-base-en-v1.5`. Before the switch, the correct page (36) did not appear anywhere in the top 15 vector search results. After the switch, it appeared at rank 4, confirming the original diagnosis that the smaller model genuinely struggled to distinguish "US business" from very similarly-worded "[other region] business" chunks elsewhere in the same report. Running the actual question through the app afterward produced a correct, accurate answer (29% revenue share, ₹168.2 Billion), though interestingly the final 3 retrieved chunks were from pages 37, 107, and 42, not page 36 itself. Page 37 appears to be a continuation of the same section and carried enough of the same information to answer correctly. A real, working fix, just not through the exact mechanism originally predicted.
- Re-ran the full 18-question evaluation set after the embedding model upgrade and hybrid search were both in place, comparing against the original results. The honest outcome: 4 questions changed from wrong or missing to correct (HDFC digital banking, HDFC emerging risks, TCS operating margin, Sun Pharma US revenue), confirming the fix genuinely worked in multiple places, not just the one case originally traced. But 2-3 questions got measurably worse on the same rerun (HDFC CSR/village figures lost a previously-correct number, TCS workforce answer became vaguer, HDFC AI customer-service answer became less coherent, reading like scrambled source text repeated rather than properly synthesized). A separate pattern also emerged on 4 questions (TCS partnerships, Reliance Retail description, Reliance solar plans, Sun Pharma risk management): the app gave a different real answer between the two evaluation runs, not wrong, just genuinely different valid content pulled from a different section of the same large report. This suggests some of these large, broad-topic reports discuss the same theme in more than one place, and a single hand-picked "expected answer" does not always capture the full range of correct responses.
- A third round of fixes (a stronger prompt instruction to synthesize in the model's own words instead of copying fragments, normalizing "%" to "percent" for BM25 keyword matching, and a modest chunk size increase from 1000 to 1300 characters with overlap raised to 200) produced two clear, confirmed fixes on retest: the previously garbled HDFC AI customer-service answer became clean and accurate, closely matching the expected content, and the previously unanswerable Sun Pharma drug launches question now correctly names real, verifiable drugs (Leqselvi, Unloxcyt) pulled directly from the report's actual launch history. Two other questions showed partial improvement without being fully fixed (HDFC CSR now correctly states the crore figure again and honestly says it can't find the village count instead of inventing an unrelated one; HUL's manufacturing investment question moved from a flat "could not find" to genuinely relevant, real content, just not the exact figure originally expected). One question (Reliance's solar energy plans) remains a genuine, unresolved weak spot, this round it produced an internally inconsistent answer, citing two different capacity targets for two different years that do not logically fit together, suggesting the model is blending multiple real but separate facts from different parts of the report rather than reporting one clean, single answer.
- Chunking at 1000 characters with 150 character overlap produced **7,995 total chunks** across all 5 reports. Sun Pharma alone produced the largest jump in chunk count relative to its page count, likely due to denser paragraph text per page compared to the others, worth watching once real question testing begins.
- First end-to-end test question, asked about HDFC Bank's digital banking initiatives, returned a specific, accurate answer pulled from 4 different pages (112, 90, 155, 233), including specific details like a named product ("y Pixel" credit card) and a real statistic (90 percent of transactions happening digitally). This is a strong early signal that the retrieval and grounding setup works correctly on real data, not just in theory.

## 5. Challenges & How You Solved Them

### LangChain text splitter import error
**Problem:** Running `chunk_and_embed.py` for the first time failed immediately with `ModuleNotFoundError: No module named 'langchain.text_splitter'`.

**Investigation:** The code imported `RecursiveCharacterTextSplitter` from `langchain.text_splitter`, which used to be the correct location in older LangChain versions. Checked the installed LangChain version and found that text splitters had been moved out of the core `langchain` package into a separate package, `langchain-text-splitters`, in a recent restructuring.

**Fix:** Installed `langchain-text-splitters` directly with `pip install langchain-text-splitters`, and changed the import to `from langchain_text_splitters import RecursiveCharacterTextSplitter`. Added the package to `requirements.txt` so this does not break again on a fresh install.

**Why this fix, not another:** Could have pinned an older version of `langchain` that still had the old import path, but that would mean giving up newer fixes and features for the sake of one import line. Updating the import to match the current package structure is the correct long term fix, not a workaround.

### Missing torchvision dependency
**Problem:** Running `app.py` for the first time failed with `ModuleNotFoundError: No module named 'torchvision'`, coming from inside the `sentence-transformers` / `transformers` import chain, not from any code written directly for this project.

**Investigation:** Some versions of the `transformers` library, a dependency of `sentence-transformers`, attempt to import `torchvision` at load time to support image-processing features. This project only uses text embeddings, never touches image processing, but the import still runs unconditionally in the installed version, so a missing `torchvision` package crashes the whole import chain rather than being skipped.

**Fix:** Installed `torchvision` directly with `pip install torchvision`, and added it to `requirements.txt`.

**Why this fix, not another:** Could have tried pinning an older `transformers` version without this import behavior, but that risks losing other fixes and compatibility improvements, and isn't guaranteed to be stable long term. Installing the one missing dependency directly is the simpler, more durable fix, even though the package itself is not used for anything in this project beyond satisfying that internal import.

### Slow response time with Llama 3.1
**Problem:** Once the full pipeline was working end to end, answers from Llama 3.1 8B took a long time to generate, long enough to hurt the actual experience of using the app.

**Investigation:** Checked whether the machine had a dedicated GPU Ollama could use for acceleration. It did not, only integrated Intel Iris Xe graphics, meaning the model was running entirely on CPU. CPU inference for an 8 billion parameter model is inherently slow, this was not a bug in the code, just the real cost of running a model this size without GPU acceleration.

**Fix:** Switched to Llama 3.2 3B, a smaller model, which noticeably cut response time. Also reduced the number of retrieved chunks per question from 4 to 3, and added streaming so the answer appears word by word as it generates instead of all at once after a long wait, which does not reduce total generation time but removes the feeling that the app has frozen.

**Why this fix, not another:** Considered keeping Llama 3.1 and just accepting the wait, but for a tool meant to be tried and demoed by other people, response time matters as much as answer quality. A faster, slightly less deep model that people will actually enjoy using is a better outcome than a deeper model that feels broken. Once confirmed working well, Llama 3.1 was removed from the project and from the machine entirely, no reason to keep two models installed once the switch was confirmed good.

### EnsembleRetriever import path, again
**Problem:** While building hybrid search, `from langchain.retrievers import EnsembleRetriever` failed with `ModuleNotFoundError`, the same category of error as the earlier text splitter issue.

**Investigation:** Checked where `EnsembleRetriever` currently lives by testing imports directly rather than guessing. Found it now lives in a separate package, `langchain-classic`, not in core `langchain` or `langchain-community`. This is now the second time in this project that a LangChain import has moved between packages mid-build, a real pattern of this specific dependency restructuring itself, not a one-off mistake.

**Fix:** Installed `langchain-classic` and updated the import to `from langchain_classic.retrievers import EnsembleRetriever`. Added the package to `requirements.txt`.

**Why this fix, not another:** Same reasoning as the earlier text splitter fix, pin an old version and lose future compatibility, or update the import to match where the library actually lives now. Chose the latter both times, for the same reason. Worth noting for future work on this project: if another LangChain import breaks, checking the current package location directly (rather than assuming the old path) is now the expected first step, not a surprise.

### No progress feedback during a genuinely long embedding run
**Problem:** After switching to a bigger, more accurate embedding model (`BAAI/bge-base-en-v1.5`) to fix the retrieval accuracy issue, running `chunk_and_embed.py` gave no visible progress at all during the embedding step, just one printed message, then silence for over 30 minutes with no way to tell if it was working or stuck.

**Investigation:** Checked CPU usage in Task Manager during the run and confirmed the process was genuinely active (58% CPU on `python.exe`), not frozen. The real cause was that `Chroma.from_documents()` embeds the entire chunk list in one call, with no progress reporting built in, and the original comment in the script ("may take a few minutes") was written for the smaller, faster MiniLM model, giving a badly wrong time expectation for the new, larger model.

**Fix:** Rewrote `embed_and_store` to process chunks in batches of 200 using `add_documents()` instead of one single `from_documents()` call, printing a running count and percentage after each batch. Also corrected the printed time estimate to be honest about the real range (30-60+ minutes on CPU-only hardware with this model), instead of understating it.

**Why this fix, not another:** Could have just left a longer wait with no feedback and accepted it, but for a script other people might run themselves (anyone cloning the repo), silently sitting for potentially an hour with zero indication of progress or failure is a real usability problem, not just a personal inconvenience. Batching also has a side benefit: if the process is interrupted partway, Chroma's `persist_directory` reflects only the chunks embedded so far, whereas a single giant call risks losing all progress on any interruption.

## 6. Limitations

- **Cross-company comparison is not supported.** The five companies span different sectors on purpose, so their reports do not share comparable metrics or risk categories. A comparison feature was considered and set aside because comparing a bank against an FMCG company head to head would not produce a meaningful answer.
- **User-uploaded reports are not supported in v1.** Only the five pre-loaded companies can be queried. Uploading your own report is a reasonably scoped next feature, left out of v1 to get the core pipeline working and tested first.
- **No automatic lookup by typing any company name.** There is no reliable, standard way to locate any given Indian company's latest annual report from just its name, since these are not published at predictable web addresses or through a shared system. This was considered and rejected as its own separate project, not a small addition here.
- **Retrieval is noticeably weaker on infographic-style stat pages than on regular prose.** Running the full evaluation set (see Discoveries above) showed that pages built as visual stat grids or dashboards, rather than written paragraphs, extract into a jumbled, hard-to-embed text order, which hurts the system's ability to find and use them correctly. Around a third of evaluation questions were affected by this in some way, either returning no answer for content that genuinely exists, or returning a real but differently-sourced answer than intended. This is a known, common limitation of text-only PDF extraction for RAG, not something unique to this project's code, and a fix would likely involve smarter page-layout-aware chunking or table-specific extraction, left as a future improvement rather than solved in v1.
- **Fixing retrieval on one question can occasionally make a different question worse.** Re-running the evaluation set after the embedding model upgrade showed real, measured gains on 4 questions, but 2-3 other questions that were correct or partially correct before became less accurate or less coherent on the same rerun. A follow-up prompt fix later resolved the coherence issue specifically (see Discoveries above), but the broader point stands: changing what gets retrieved for one question can shift what gets retrieved for a nearby, differently-worded one, not always for the better. This is a normal, honest trade-off in retrieval tuning, not something this project has fully solved, and is worth remembering before assuming any single fix is a clean, universal improvement.
- **Answers to broad questions on large reports are not always consistent between runs.** On questions like "what are the company's plans for X" asked against a 300+ page report, the app sometimes surfaces a different real section of the report on different runs, since the same broad theme is often discussed in more than one place. The answers given have generally still been accurate to some real part of the report, just not always the specific passage expected, which is a softer problem than a wrong answer, but worth knowing about, especially for reproducibility if this app is demoed more than once with the same question.
- **On some broad questions, the model blends multiple real facts inconsistently, sometimes producing an internally contradictory answer.** Reliance's solar energy plans question is a clear example, across three test rounds it produced three different sets of numbers, and on the most recent round, the answer cited two different capacity targets for two different years that don't logically fit together as a single roadmap. This suggests the report discusses solar plans in more than one place with genuinely different figures, and the model isn't reliably picking one coherent thread to report, it's mixing them. Unresolved as of this writing, a deeper fix (like teaching the model to notice and flag when retrieved chunks conflict, rather than blending them silently) is a real v2 idea, not attempted here.

- **`chunk_and_embed.py` built and tested:** Splits each page's text into 1000 character chunks with 150 character overlap, embeds them using the free Hugging Face model `all-MiniLM-L6-v2`, and stores everything in Chroma with company, sector, and page metadata attached. Hit and fixed a LangChain import path issue along the way (see Challenges section). Final run produced 7,995 chunks across all 5 companies, stored successfully in the local vector store. Next step is building the retrieval and answer chain.
- **`retrieve_answer.py` built and tested:** Filters retrieval to a single company using Chroma's metadata filter, builds a prompt that restricts the LLM to only the retrieved context, and generates answers using Llama 3.1 running locally through Ollama, chosen over Anthropic or OpenAI's paid APIs (see Tech Stack section). First real test question against HDFC Bank's report returned a specific, accurate, correctly cited answer. Core RAG pipeline is now working end to end. Next step is building the Streamlit interface.
- **Evaluation set built:** 18 question and expected-answer pairs written across all 5 companies (6 for HDFC Bank, 3 each for the rest, weighted since HDFC Bank's report is by far the largest), stored in `eval/qa_test_set.xlsx`. Every expected answer was pulled directly from the real report text, not guessed, with the exact source page(s) noted for each.
- **Evaluation run and results reviewed:** All 18 questions asked in the running app, actual answers compared against expected answers. Roughly a third of questions returned wrong or missing content, with failures clustering specifically around infographic-style stat pages rather than regular prose (see Discoveries and Limitations above). Root cause identified and documented, not yet fixed. Hybrid search identified as the concrete next step to address this (see Still Open below).

Known retrieval accuracy issue on infographic-style pages is documented, not hidden, with a specific planned fix (hybrid search) rather than left as a vague "known issue."
- **Hybrid search built and wired into the app.** Added BM25 keyword search alongside vector search, combined via `EnsembleRetriever`, and wired into `app.py` with per-company caching so the keyword index isn't rebuilt on every question. Diagnosed one specific failing case (Sun Pharma US business revenue) down to the actual root cause using two purpose-built diagnostic scripts (`diagnostics/diagnose_chunk.py`, `diagnostics/diagnose_ranking.py`), confirmed it was the embedding model's resolving power, not the search method or chunk count.

Re-tested the previously failing Sun Pharma question directly afterward: correct chunk moved from completely absent in the top 15 results to rank 4, and the app produced a correct, accurate answer. First concrete, measured proof that the retrieval accuracy work actually improved something real, not just theoretical.
- **Third tuning round: prompt fix, BM25 normalization, chunk size increase.** Fixed the answer-coherence regression with an explicit prompt instruction to synthesize in the model's own words rather than copy fragments. Fixed the literal "%" vs "percentage" keyword mismatch by normalizing both stored chunks and incoming questions before BM25 comparison. Increased chunk size from 1000 to 1300 characters (overlap 150 to 200) and rebuilt the vector store again. Retesting confirmed two clear fixes (HDFC AI customer service coherence, Sun Pharma drug launches) and two partial improvements, with one genuine unresolved case remaining (Reliance's solar plans question still blends multiple real facts into an internally inconsistent answer). Stopping retrieval tuning here for v1, real gains achieved and documented, with clearly named remaining limitations rather than an open-ended chase for a perfect score. Moving to deployment next.
- **Deployment investigated and deliberately not pursued.** Measured real memory requirements directly (Windows process monitoring during actual use), checked real numbers against Render's tiers and Streamlit Community Cloud's limits, and evaluated switching the deployed LLM to a free hosted API (Groq) as a way to reduce cost. Concluded that even with that swap, the app's own memory footprint requires a paid hosting tier (at minimum $25/month), and made the deliberate decision to stop there rather than keep adding infrastructure changes under time pressure. The full RAG pipeline is complete, correct, and demoed locally. **v1.0 considered feature-complete** at this point, with deployment marked as a known, reasoned, and clearly documented decision rather than an unfinished task.
- **v2.0 started: revisiting deployment with a different architecture.** Further research after v1.0 identified that the deployed container's memory problem came from two specific pieces, the vector store and the embedding model, neither of which need to run inside the app itself. Decided to move chunks to a hosted vector database (Pinecone, free tier, confirmed to comfortably fit this project's 6,282 chunks) and query-time embedding to a hosted Hugging Face API, alongside the already-scoped Groq swap for the LLM. Local development is unaffected and keeps using Chroma and a local embedding model exactly as built in v1.0. Same RAG pipeline, same LangChain orchestration, same evaluated retrieval logic throughout, this is a hosting change, not a rebuild.
- **All 6,282 chunks migrated to Pinecone, verified.** Built `migrate_to_pinecone.py`, which reads each chunk's already-computed embedding directly out of Chroma (no re-embedding) and uploads it to Pinecone in batches of 100, including the chunk's text inside its metadata since Pinecone doesn't store document content the way Chroma does. Hit one real bug along the way: Chroma returns embeddings as NumPy numbers, which Pinecone's JSON encoder can't serialize directly, fixed by explicitly converting each value to a plain Python float before upload. Final run uploaded all 5 companies successfully, and Pinecone's own `describe_index_stats()` call independently confirmed 6,282 total vectors stored, matching the local Chroma count exactly.
- **Hugging Face's hosted Inference API confirmed working for query-time embedding.** Before wiring this into the real pipeline, tested it directly with a real API call using `BAAI/bge-base-en-v1.5`, the exact same model used locally. Returned a 768-dimension embedding, matching both the local model's output and Pinecone's configured index dimension exactly. This resolves the real uncertainty flagged earlier about free-tier availability for this specific model, confirmed by direct test rather than assumed from documentation.
- **Decided to keep full hybrid search in the deployed version too, not just vector search.** Pinecone isn't built for "give me every chunk for company X" the way Chroma is, which made BM25 keyword search awkward to support for the deployed version at first. Solved by exporting each chunk's text and metadata (deliberately excluding the embedding vectors, which BM25 doesn't need) into small JSON files, one per company, that ship as part of the app's own code. Total export size across all 5 companies: about 7.7MB, small enough to commit directly to the repository, comfortably smaller than the 85MB of source PDFs already tracked. This means the deployed version can build the same BM25 index instantly at startup, no network fetch needed for the keyword half of hybrid search, while Pinecone handles the vector half over the network.
- **Cloud retrieval built and verified (`retrieve_answer_cloud.py`).** Mirrors the local hybrid retriever's structure exactly, vector search via Pinecone (using a custom LangChain-compatible embeddings class that calls Hugging Face's hosted API instead of loading a model locally) combined with BM25 keyword search (built from the exported JSON files). Retested the same Sun Pharma US business question used throughout this project's retrieval debugging, and the cloud path retrieved the exact target page (36) directly, alongside real adjacent context, genuinely matching or exceeding the local hybrid search's result on this specific case. One small bug found and fixed along the way: Pinecone returns numeric metadata as floats (e.g. `37.0` instead of `37`), while the local BM25 path returns clean integers, fixed with a small normalization helper so page citations display consistently regardless of which retrieval method found the chunk.
- **Groq LLM wired in, full cloud pipeline confirmed end to end.** Originally planned to use `llama-3.1-8b-instant` on Groq, matching the local Llama model family, but Groq deprecated that model in June 2026. Their own migration guidance pointed to `openai/gpt-oss-20b` as the direct replacement, still free, still fast, but an OpenAI open-weight model rather than Llama, worth being accurate about since it's a genuine, if minor, deviation from the original plan. Local development is unaffected and still uses Llama 3.2 via Ollama. Also hit and fixed a small type-checker issue: `ChatGroq` expects the API key wrapped in Pydantic's `SecretStr` type rather than a plain string, a real security-conscious design choice on LangChain's part (prevents keys from accidentally appearing in logs), not just a formality. Full pipeline retested on the same Sun Pharma question: Pinecone retrieval, Hugging Face query embedding, and Groq answer generation all working together correctly, producing a correct, accurate, properly cited answer (29% revenue share, grounded in page 36). This confirms the entire v2.0 architecture works end to end, not just each piece in isolation.
- **Dockerfile built, containerized, and deployed locally for real memory testing.** Built a lean, cloud-only `requirements-cloud.txt`, deliberately excluding torch, sentence-transformers, and Chroma, none of which the deployed path uses. Docker image built successfully on the first real attempt. Ran the actual container locally with `docker run`, asked a real question through the browser, then measured live memory usage with `docker stats`: **185.3MB total**, compared to v1.0's measured ~941MB app plus ~2GB for a locally-run LLM, a real, verified reduction of roughly 94%. This comfortably fits Render's free tier (512MB limit), with over 300MB of headroom remaining. This is the concrete, measured confirmation that the entire v2.0 redesign, moving storage to Pinecone, query embedding to Hugging Face's API, and the LLM to Groq, actually achieved its goal, not just in theory but verified at every step with real numbers.
